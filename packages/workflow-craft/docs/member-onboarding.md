# 团队成员接入与日常协作

首次启用先用 `doctor --local` 确认项目模式；没有配置时询问个人/团队，有模式时沿用。个人本地流程及后续模式切换见 [开发模式](../skills/workflow-craft/references/development-modes.md)。下文适用于团队平台流程，个人不需要为启动本地任务配置平台或集成人。

本指南用于已获批准的团队仓库，只描述通用接入与协作步骤。项目当前仓库内容、负责人、平台权限、凭据处置与部署切换以该项目的维护文档和现场检查为准；这些步骤本身不授予代码导入、生产切换或账号创建权限。AIOS 的接入与历史部署资料由 AIOS 仓库维护（`docs/CNB_TEAM_ADOPTION.md`、`docs/archive/gitea-vps/`）。

每人用个人账号开发任务分支和发起 PR，集成与合并沿用项目批准的人工或队列流程；组织名称不能替代成员身份，不使用负责人的账号代表所有人提交。账号、负责人角色与 Token 有效期分别管理，凭据期限按公司批准策略设置，不把某位成员的选择作为全员默认。个人凭据不得共享。

## 负责人准备一次

准备一个低风险试点任务：平台 Issue 写清目标、范围、验收、接口依赖和集成负责人。已有规格直接引用。为成员提供仓库 URL、批准的 Skill ZIP 与独立确认的 SHA-256、项目检查命令及测试资源命名规则；不要提供共享账号或 VPS 凭据。

| 身份 | 所需权限与责任 |
| --- | --- |
| 平台管理员 | 建账号、私有组织与仓库，维护备份/恢复；不作为全员共用身份 |
| 开发者 | 自己账号、仓库开发权限、任务分支/PR；目标为无 main 直推、强推、生产部署或合并权限，实际限制需平台验收 |
| 审查者 | 足够理解变更的独立成员，读取任务/diff/证据并确认当前 head；作者不自批 |
| 集成/发布负责人 | 核对最新基线、审批、验证和组合功能，按项目集成流程交付；按另行授权发布固定版本 |

CNB 的开发者角色默认包含合并权限，必须配置保护规则并单独验收普通成员是否可合并；管理员批准不等于只允许管理员点击合并。实际账号与团队称呼分开：负责人称呼与 CNB 的真实 username/ID 分开，以本人账号读取为准，不修改组织名或猜测账号。

可选 Gitea 平台默认允许有 write 权限成员的审批计数。成员身份确定后，负责人按项目风险配置可信审查者 allowlist 并实测；创建名为 Reviewers 的团队本身不自动形成审批限制。至少需要两位真实成员，单一账号不能完成独立审批试点。

每人按所选平台完成个人登录、账号保护与恢复渠道配置。自托管 Gitea 邮件未启用时不要依赖邮件重置；第二恢复渠道应由负责人明确交接。新成员名单未确定时不创建猜测账号或共享实习生账号。

## 成员第一次使用

1. 用自己的账号访问仓库，在自己电脑建立独立 clone。Git HTTPS 凭据使用操作系统或批准的凭据管理器；不把密码/Token 放进 URL、终端命令参数、项目文件或聊天。
2. 仓库里已提交 `.agents/skills/workflow-craft/` 和 `.claude/skills/workflow-craft/` 时，clone 下来就能用，不用另外安装。否则由负责人按 [固定产物安装](../README.md#固定构建与项目安装) 安装一次并提交；只有项目不允许提交时，成员才各自安装项目副本。不复制另一人的全局配置。TWC 不依赖 Trellis；AIOS 使用 Trellis 托管模式，但没装 Trellis 的成员同样可以用 TWC。
3. TWC 使用个人只读 Token。CNB 分别配置仅目标仓库的 `TWC_CNB_TOKEN` 和仅账户信息的 `TWC_CNB_IDENTITY_TOKEN`，六项读取权限见 [CNB 接入](../skills/workflow-craft/references/cnb.md)；实际账号仍需仓库可见权限。Gitea 使用 `TWC_GITEA_TOKEN` 与所需 read scopes。不要复用管理员写 Token。
4. 在所用宿主的新会话显式调用 Skill，先运行 `doctor --local`，按 `next_steps` 补齐项目配置或修正安装副本。首次只需名字或团队称呼：已有 `member.name` 就复用；出现 `configure_member_name` 时，Agent 只询问名字（例如“67”），不索要邮箱，获准后按 [成员身份](../skills/workflow-craft/references/identity.md) 在自己的 clone 设置 `user.name`。实际提交、正式交接时再核对已有 Git 提交身份；平台读取获准后运行 `doctor --online` 和 `workspace inspect`，核对平台 login 是本人、Git author/committer 正确。平台显示名可填写中文姓名，TWC 的个人只读 Token 与 Git push 的个人凭据分别配置。记录宿主/OS 版本、实际加载路径、产物哈希；文件安装成功不能代替会话加载验收。
5. 读取任务和项目规范，确认验收及资源隔离，再开始修改。端口、测试数据库、Redis key、Docker 项目名和输出目录按任务隔离；不得用生产数据环境完成实习测试。

## 每个任务只走一条链路

已有干净 clone 时从最新 main 建短任务分支，如 `feat/alice/42-material-search`。名字只是辨识提示，不授予独占或合并权限。Issue 分配给实际负责人，任务契约的 `integrator` 填项目批准的集成负责人，并在需平台权限匹配时核对其实际 username/ID。明确本次范围，实施后按已批准检查执行验证，提交自己的文件，并为提交后的 SHA 重新验证，再经授权推任务分支并建立 PR。其他人的 WIP 保留；TWC 不自动 commit/push，也不替代项目原有授权规则。

PR 至少能定位任务、目标/非目标、实际变化、验收证据及未完成项。PR 处理人指派给项目批准的集成负责人对应的实际平台账号；正式启用前以普通开发者账号验证其他人不能代为合并。处理人机制不能仅凭填写成功宣称权限隔离完成。交接人必须能从平台取得已推送分支和资料；本地绝对路径或未推送提交不算交接完成。TWC 只在任务目录写交接，提交、推送和在 PR 发布由获授权成员完成。

接续由 TWC 记录的任务时先运行 `resume`；`next_actions` 是待办清单，按当前目标和项目规则选择执行时机，不要求开工前先重验。切分支后若提示绑定冲突，核对当前任务后运行 `prepare --rebind`，不沿用上一任务。正式交接使用 `verify --execute --approved-policy <已批准策略哈希> --online` 与 `handoff --draft --online ...`，分别记录本次验证者和交接者；然后带 pathspec 提交 `.team-workflow/tasks/<task>/` 并推送分支。接手者切到该分支后先 `resume`，核对自己的身份，仅在绑定缺失/冲突或审阅后契约变化时 prepare；不修改旧证据的名字。离线可工作，平台身份未知时补充联网验证再交付。要看“谁做了什么”，从 Issue → PR → 提交作者 → 验证者 → 合并者这条链路查看，不单凭分支名或提交数量评价贡献。

负责人串行集成：更新基线 → 重验组合 → 审查者确认当前 head → 核对审批与平台门禁 → 合并。Gitea 仅合入 main 时可能保留旧内容审批；CNB 的新提交、基线变化与审批策略要分别验收。任何平台都要重新验证新的 head/base。审批和代码测试是两种证据。

初期其他开发者的 PR 可由集成负责人审查并合并；负责人自己开发的 PR 需要另一位合适成员审批，再由获授权的负责人合并。角色与人员可以重叠，作者不自批的规则仍适用。

普通成员不执行 VPS push guard、部署、数据库迁移或镜像清理。项目涉及旧 hook、历史凭据或生产来源切换时，在正式接入前由项目负责人核对处置状态并验证规则；不要把 VPS 密码发给成员来绕过这一前置条件。

## 第一轮完成标准

一位成员用 Claude 开始，另一位用 Codex 从平台资料接手，第三位用 Pi 复核；使用独立账号和 clone，完成真实任务、审批及组合验证。临时测试账号、自动化 Git/REST 验证和三个 Agent 都说“完成”均不能代替这轮验收。

提交 SHA、镜像身份、生产部署、GitHub 单向同步分别留证。当前没有 CI 时明确记为未接入，不填模拟的绿色状态，也不把本地验证当成服务器门禁。
