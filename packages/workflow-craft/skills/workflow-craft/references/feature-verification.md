# 功能验证路径

在关键功能涉及实际操作、入口难找或验收覆盖不清楚时读取。先找项目现有测试、操作说明、验收案例和工具；已有路径直接引用，只补当前任务缺失的部分。简单修改不强制建图、建文件或扩展 CLI；不一次绘制全项目功能。

动手前说明将用什么证据判断目标达成，并标出目前无法验证的环节。自动检查、真实界面操作和人的体验判断各自证明什么，要与验收条件对应；单元测试通过不能证明界面或整条业务流程可用。需要重复执行且现有工具确实缺失的动作，再补成项目可维护的脚本或命令；不重写已有测试框架。

一条路径应让下一位使用者能够复现，按项目既有格式记录这些信息即可：

| 信息 | 需要回答的问题 |
| --- | --- |
| 入口与前提 | 从哪里进入？用哪个角色、数据或环境？ |
| 操作 | 按什么顺序做，输入是什么？ |
| 预期结果 | 能观察到什么，如何与原始数据核对？ |
| 容易误判的地方 | 哪些空状态、权限、边界或缓存会造成假通过？ |
| 验证方法 | 复用哪个准确命令、现有工具或人工步骤？证据在哪？ |
| 重复与清理 | 操作会写什么？如何隔离、恢复或安全重跑？ |

优先使用项目现有工具；环境已有 browser67 等真实操作工具时可复用，不把某个浏览器工具变成 Skill 的必装依赖。涉及付款、删除、发布等外部动作时，使用已批准的测试环境与数据；验证路径本身不授权执行。

例如“退款导出”的路径可串起：进入退款列表 → 选择明确的日期边界 → 导出 → 核对文件条目与金额 → 检查空结果与无权限情况 → 重新打开确认状态。对应单元测试可核对日期及金额，真实界面操作确认入口和下载，权限验证使用项目批准的角色和环境。这只是路径写法示例，不新增任何产品需求。

入口、行为、接口或数据口径变化时，同步维护受影响的路径、检查脚本及验收映射；复用原文件，不建立第二份规格。已确认缺陷保留能再次发现它的回归案例，先排查同类调用点再决定修复范围。无法确定性判断的体验保留人工验收；相关 AC 仍为 `needs_review`。交付时报告实际执行结果、证据位置及未覆盖环节；维护频率由真实变化决定，不设置无必要的定期全量重验。
