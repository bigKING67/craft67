# 双盘分歧：经复核的五个追问答复

出生资料和问题见 [requests.json](requests.json)。A、B 是未验证的用户转述；C 是明确的人为推理假设，不代表本次真实命盘已经生成了相反结论。D、E 有实际本地计算证据，见 [computation.json](computation.json)。

## A：不同年份、不同安排，是不是冲突？

不能据此认定冲突。“2026多承担工作”与“2027少社交”涉及不同时间和行为，可能同时执行，但相容不等于已经互补。目前分类为 **insufficient**：既缺两份原始论证，也没有统一成一个可比较的问题。

如果你要问的是“未来两年的工作与社交怎么安排”，可以先分别核对每条判断，再讨论两者如何衔接；如果只问2026是否接一个项目，2027社交建议不能直接作为支持或反对票。现在的缺口是各自指什么行为、适用时间及依据，而不是再找一个总分。

## B：有财线索＋官禄压力，能不能说两边支持升职？

不能。财的线索不等于升职，工作压力也可能来自任务量、组织变化等不同现实原因；两句话没有分别论证同一个“升职”结论，分类是 **insufficient**。

本例财格条件模块为 outside-scope/unresolved，只说明特定月令财星透出的检测入口未满足，不是“无财”，更不是晋升判断。实际是否有晋升机会，还需岗位、评审和职责变化资料；不能把这种现实资料缺口用两个命理标签填满。

## C：同条件下一个说接项目，一个说不接，必须选哪一个？

在你给定的推理假设里，**conflicts 成立**：两份判断针对同一个行动，且前提一致，无法同时执行。但这组前提没有提供选择哪边的依据，我不能把“必须选一个”当成新增证据。

也不能自行假定“不接更安全”或“可以随时反悔”：拒绝可能失去机会，接下可能有退出条款，题目都没有说明。可具体比较项目工期、必须承担的责任、退出安排和放弃的代价；如果你另行指定“优先保证现有交付”这样的决策偏好，可以据此取舍，但那是明确的现实选择标准，不是证明哪套命盘更正确。

此题6月的两个建议完全来自假设。当前CLI仅提供年度层，不能冒充已计算出这两项月度建议。

## D：2026-02-10 一边丙午、一边乙巳，是算法错吗？

按本项目的年界设置，这个差异符合预期。安装库本地计算给出：2026年立春为固定UTC+8的2月4日04:02:08，农历新年为2月17日。2月10日12:00处于二者之间，所以八字已进入丙午年，按农历新年切换的紫微流年仍为乙巳年。

这是**年界口径核对**，无需登记成跨体系“互补”。它还没有提出一个待支持、反对的命理结论；若被迫放进报告四分类，只能说明不足以据此建立跨体系结论，不能把标签不同当成冲突。对老师实际使用的流派与软件，本次没有核对。

复算还检查了2月3日两者同为乙巳、2月17日两者同为丙午；数值来自当前依赖实现，不宣称独立天文精度认证。

## E：保留旧八字，只更新紫微，是不是更全面？

不是。出生时间从14:20改成14:50，本例真太阳时从未时跨到申时：八字时柱由己未变庚申，紫微命宫由卯变寅、身宫由巳变午。只更新一个体系会混入两种出生假设。

因此这里是**输入不可比**，不是同一候选内的 conflicts。若必须登记四分类，则为 **insufficient**，理由是比较前提未对齐。确认14:50后应两个体系一起重算；若两种时间都未确认，则并列两份完整候选，分别讨论共同点和差异，不拼成一张盘。

## 事实复现

在项目已 build 后运行：

```sh
node examples/acceptance/cross-system/verify-facts.mjs
```

脚本检查年界和两种出生时间的计算结果，不调用模型、网络或账户接口，也不自动判断上面自然语言分类是否正确。语义结论由人工复核，不能用脚本通过冒充语义自动验收。
