# 最小真实验收方案

状态：方案已准备，真实执行未授权。机器可读入口为 [live-acceptance-plan.json](live-acceptance-plan.json)，其中 `stages[].argv` 是现有 CLI 的参数数组，不是自动执行队列。

本方案验证当前修复后的三个代表领域，不替代八领域完整验收，也不据三个案例宣称普遍效果提升。模型、实际费用预算和运行环境必须在执行前确定；计划不默认为用户批准任何模型。

宿主能力与本次接入范围见 [加载证据核查](host-loading-evidence.md)。执行事件摘要与可选 App Server 输入收据已接入，但加载验收条件仍未满足。参数清单现为 POSIX App Server 候选执行路径，Judge 仍使用 exec；两条路径的认证与隔离设置需分别核验。

## 执行前条件

1. 核对工作区和计划中的输入摘要，冻结本次源文件及 Bundle 摘要。保留已有 WIP。
2. 为产物创建一个新的私有真实目录，替换 `{artifact_root}`；替换 `{model}` 为明确批准的模型。目录不得经过用户创建的软链接，文件不得覆盖历史结果。
3. 使用现有 `verify_install.py` 只读核对默认发现根的内容。内容不一致时停止，另行处理安装授权，不能跳过检查或改用自定义根伪造加载一致性。
4. 确认宿主能够提供本次调用的 Skill 加载证据。现有执行器记录 `runtime_skill_loading_verified=false`；可选 App Server 路径新增输入接受收据，但尚无宿主注入字节收据，因此**当前不能通过加载验收**。先补齐宿主证据采集，再启动正式模型验收；若另行批准仅做生成探索，其结果必须标为探索样本。
5. 不直接从计划自动运行命令。按阶段执行并检查结果，前一阶段失败就停止，不自动重试，不自动进入后续阶段。

## 调用预算

| 阶段 | 调用数 | 单次超时 | 阶段条件 |
|---|---:|---:|---|
| 商业案例加载 smoke | 1 | 300 秒 | 加载证据合格后才继续 |
| 商业、运营、分析分别生成并 Judge | 6 | 300 秒 | 每案例 2 次，单案例总预算 660 秒 |
| 三领域固定正反例校准 | 6 | 180 秒 | 每领域 1 正例、1 反例，单次判定 |
| 合计 | **13** | 模型超时之和 3,180 秒 | 失败调用也占用预算，无自动重试 |

加载 smoke 与正式生成独立记录，因此商业生成明确计入两次。三个质量命令只启用 execution 和 judge，不附带 selection 或全量 calibration。固定校准显式选择六个案例，不运行全部二十个样例。

调用数不是 Token 或金额上限；没有批准的 provider 费用限制时，不能宣称费用已受控。各命令的总时限独立，安装检查、调度与清理有额外耗时，3,180 秒也不是全流程墙钟硬上限。

## 通过标准

- **加载**：需要与本次调用绑定的宿主记录，能定位默认发现根下的 Skill 路径与所加载内容摘要。安装 parity、提示词中的 `$skill`、模型自述或非空答案均不算加载证据。当前入口对此保持未验证。
- **商业（合同修订 v2）**：在题目成本口径及明确假设下，正确区分商品毛利、扣已知费用后的广告前贡献和扣广告后的利润，给出可核算的金额、公式或等价比率。参考为商品毛利 165,000 元、广告前贡献 111,000 元（37%）、扣广告后贡献利润 -39,000 元、盈亏平衡 ROI 约 2.70。金额与公式完整时不强制列举所有派生比率；若使用毛利 ROI，应为 1.10，广告前贡献／广告费为 0.74，不得混称。不得仅凭平台 ROI 支持预算翻倍，未知成本不得视为已确认零成本。预算上限须绑定收入、成本和目标利润假设；测试、止损和放量参数须说明依据、适用范围及待确认项，不得把示例参数当作既定护栏。原条款与修订依据见 [验收合同修订记录](acceptance-contract-revisions.md)。
- **运营**：14 天安排能够落实到排品、库存、场控、客服、履约和退款异常；责任、升级、恢复条件、复盘信号完整。缺失数据显式列出，不虚构当前平台规则。
- **分析**：观察事实、可能解释、归因限制、下一证据明确分开。不得将相关性写成因果，也不得在商业护栏未确认时自设放量阈值。
- **Judge**：三个生成案例通过当前 rubric，且人工复核以上关键不变量。固定三正例应接受、三反例应拒绝；出现任何不一致即停止质量门禁结论并保留原始结构化响应，不靠自动重跑挑选通过样本。
- **恢复**：运行错误显式记录；超时后检查本次受管进程是否退出。沿用现有本地进程回归证据，真实 Windows 仍须单独验收。

## 无 Skill 对照暂不执行

现有执行器没有可验证的 Skill 禁用入口。仅删去 `$skill`，或者在提示词里写“不要使用 Skill”，无法排除自动发现或内容污染，不构成有效对照。

准备对照前需证明控制组确实不能加载 Skill，并保持模型、任务、采样设置、工具权限和外部信息条件一致。两组答案匿名排列，由人工盲评正确性、领域边界与可执行性；Judge 自评不能单独证明增益。对照调用不包含在上述 13 次预算内，单独制定和批准预算。

## 证据与正式报告

保存精确源码与安装摘要、任务及答案摘要、加载收据、实际模型、耗时、调用次数、错误、Judge 原始结构化响应和人工分歧说明。不得保存凭据或无关的完整宿主日志。

将结果区分为 `PASS`、`FAIL`、`UNVERIFIED`；加载缺失或对照被污染时，对相应效果结论使用 `INVALID SAMPLE`，不把所有生成结果升级为正式通过。

下次正式审查应在创建 run 之前配置与真实 argv/cwd 一致的验证命令，并通过结构化输出声明关键阶段，再由规范 runner 捕获收据。当前方案文件不改变审查配置，不把既有手工测试补写成规范命令执行记录。

本地准备只检查计划 JSON、案例和参数是否匹配现有实现；不执行计划中的模型命令。提交、安装、push 和发布仍按各自授权处理。
